# Changelog

What changed in each phase of `PLAN.md`, step by step. Open problems live under "Known issues and follow-ups" in `PLAN.md`.

## Phase 7: Other servers and sign-in

### Changes
- **7.1 Unsupported servers.** Signing on to a server without simplified sliding sync (MSC4186) now says so ("example.org doesn't support simplified sliding sync (MSC4186), which AIMtrix needs. Ask its admin, or use another server.") instead of signing on and failing every sync. The check runs before logging in, so the server gets no device and nothing is saved. If a resumed session's server loses support, the Buddy List status bar shows the same message instead of a raw sync error.
  - `check_sliding_sync` in `matrix/mod.rs` reads `/versions`; sync errors ask again with the cached answer cleared (`sliding_sync_gone`). Any failed sign-on now also deletes the store it created.
  - `dev/old-server.py` is a fake homeserver without the feature, on `http://localhost:8010`, for checking it by hand. A unit test runs a similar fake server and checks no `/login` is sent.
- **7.2 continuwuity.** AIMtrix now works on continuwuity (the community continuation of conduwuit), not just Synapse: sign-on, the Buddy List, IMs, Chat Rooms, presence and encryption. Fixed along the way, for any server that behaves like it:
  - Presence on a new account with no rooms: continuwuity shows presence only to people sharing a room, you included, so AIMtrix decided the server had none for the whole session. It now tries again until it can tell. A server that refuses presence outright (403) now counts as having none, instead of being retried forever.
  - People joining and leaving: continuwuity sends these only in the timeline, not as sliding sync state, so the SDK never stored them. Chat Room member lists went stale and room keys would skip people who joined later. A member event that doesn't match the stored member (`sync::notice_member_changes`), or a member count that doesn't match the list (`members::list`), now reloads the room's members from the server. On Synapse neither happens.
  - `dev/docker-compose.yml` has a `continuwuity` profile on `http://localhost:8011`. `dev/seed.py` and the tests register users with a registration token where Synapse's admin API is missing, the server tests run against any seeded dev server with `AIMTRIX_HS` (90 of 92 pass on continuwuity; the two gaps are under Known issues), and dev builds list it in Sign On's servers. The Chat Room member test now cleans up its room even when it fails.
- **7.3 Matrix Authentication Service in dev.** A dev Synapse behind Matrix Authentication Service (MAS), set up like matrix.org, confirms AIMtrix works there: password sign-on through MAS's compatibility layer, wrong-password messages, sign-off, resuming, encryption, recovery and verification all pass (92 of 92 server tests). Resetting an encryption identity needs approval in MAS's web page instead of a password, as on matrix.org; AIMtrix never resets one, and new accounts upload their first keys without approval.
  - `dev/docker-compose.yml` has a `mas` profile: Synapse delegating to MAS (`dev/synapse/mas.yaml`), MAS with Postgres on `http://localhost:8014` (`dev/mas/config.yaml`), and nginx on `http://localhost:8013` sending `/login`, `/logout` and `/refresh` to MAS and the rest to Synapse (`dev/mas/nginx.conf`). Dev builds list it in Sign On's servers.
  - `dev/seed.py` and the tests make and deactivate users through MAS's admin API when the server's `/register` is refused. The tests approve identity resets the way MAS does (`approve_identity_reset`).
- **7.4 Sign on with your browser.** On servers that support OAuth (matrix.org, MAS, continuwuity), Sign On shows **Use Browser…**: your browser opens the server's own sign-in page, and once you allow AIMtrix the Buddy List opens. This is how accounts without a password sign on, such as matrix.org accounts made with Google, GitHub or Apple; on a server with no password sign-on at all, the password fields give way to a single **Sign On with Browser…** button. While it waits there's a **Cancel** button (it gives up after 10 minutes), and refusing in the browser says so. The session survives restarts, its expiring tokens are refreshed and saved as they change, and Sign Off revokes the token.
  - `sign_on_methods` reads the server's login flows and `/auth_metadata`. `sign_on_with_browser` uses the SDK's OAuth (dynamic client registration, authorization code with PKCE) with a loopback redirect from the SDK's `local-server`; the address is registered without its port (RFC 8252), which continuwuity requires. The browser opens with `tauri-plugin-opener`, so the `.deb` now depends on `xdg-utils`.
  - The keyring holds either kind of session (`SavedAuth`); sessions saved before still load. `sync` saves refreshed tokens (`save_refreshed_tokens`), under a lock so a refresh during Sign Off can't bring the session back. The SDK only revokes over https, so on plain-http servers AIMtrix revokes the token itself.
  - The dev MAS has a Dex container, "Dev Provider (like Google)", whose account `dana` has no password, and 60-second access tokens so refresh happens while testing. continuwuity advertises its dev address for OAuth. Tests play the browser on both servers: no-password sign-on, refresh, restart, sign-off, refusing, cancelling.
- **7.5 matrix.org.** Checked by hand with a real matrix.org account: signing on with a password and with **Use Browser…** both work.

## Phase 6: AIM extras

### Changes
- **6.1 Presence.** On servers with presence, the Buddy List splits DMs into an Online group (online and away buddies) and an Offline group at the bottom, as in AIM. Favorites stay put but grey out when that person is offline. On servers without presence (matrix.org included), DMs stay in Buddies, sorted by recent activity. Signing off sets you offline first.
  - Sliding sync carries no presence, so `matrix/presence.rs` sets you online, reads it back to see whether the server keeps presence at all (a server without it says "offline" for everyone), then sets you online every 20 s and polls each DM buddy's presence just as often.
  - `dev/docker-compose.yml` has a `no-presence` profile: a second Synapse on `http://localhost:8009` with presence off (`dev/synapse/no-presence.yaml`), seeded with the same users and rooms. Server tests cover both servers.
- **6.2 Away messages.** The Buddy List's new **Away…** button opens an Away Message window. **I'm Away** sets you away with that message, and the Buddy List then shows "You're away: …" with **Edit…** and **I'm Back**. Away buddies show in grey italics, with their away message on hover, and an IM window with an away buddy shows it in a yellow banner. Other clients see you as Away; Element Web shows a grey badge but not the message text. On servers without presence the Away button is disabled.
  - Away is presence `unavailable` plus `status_msg`. The presence tracker now lives in the session, so commands can reach it, and sends your own state to windows as `presence:update`. The 20 s heartbeat resends your away message so it sticks.
  - Polling buddies and the heartbeat now run separately, and the heartbeat waits after you change your away state, to stay within Synapse's default limit of one presence update per user every 10 s.
- **6.3 Add Buddy.** The Buddy List's new **Add Buddy…** button opens a window that takes a Matrix ID (`@bob:matrix.org`) or just a name on your own server (`bob`). AIMtrix starts an encrypted DM, lists it in `m.direct` and invites them; it shows up under Buddies. If you already have a DM they're in, it opens that conversation instead. Typos get a clear message ("There's no one called …", "… isn't a Matrix ID") rather than an empty room.
  - The user's profile is checked before creating the room, since Synapse invites people who don't exist without complaint. It reports a missing user as a 404 with `M_UNKNOWN`, so the check goes by the status code.
  - Adding the same buddy twice, even at the same moment, makes one DM: adds run one at a time, DMs made this run are remembered (a new DM reaches `m.direct` a sync later), and a room of just the two of you counts as a DM too. The window also ignores a second submit while the first runs.
  - Sign On shows the server's own message when it refuses for a reason other than the password, such as matrix.org's "You have reached your hard device limit", and logs the reason.
- **6.4 Send files.** IM and Chat Room windows have a **Send File…** button (an Open dialog that takes several files), take files dropped on the window (with a dashed outline while you drag), and send a picture pasted into the message box after asking "Send the pasted picture … to Bob Brown?". The status bar shows "Sending beach.jpg (2 of 3)… 45%" with **Cancel**. Files over the server's upload limit, and folders, are refused before anything is sent. Images go with their size and dimensions, and big ones with an 800×600 thumbnail, like Element's; in encrypted rooms the file and thumbnail are encrypted.
  - `matrix/upload.rs` prepares files and thumbnails (`image`, `mime_guess`); uploads go through the timeline's `send_attachment`, with progress sent to the window as `room:<key>:upload` events. Each window sends one batch at a time, and closing it cancels the batch.
  - WebKitGTK doesn't hand pasted pictures to the page, so for a paste without text, Rust reads the system clipboard (`arboard`, which also works on macOS, Windows and Wayland). Pasted pictures reach Rust as a raw IPC body rather than JSON.
  - The image crates are optimized in dev builds so thumbnails are quick. `cargo remove` had quietly deleted the dev-profile entries for the recovery hash crates; they're back, with a warning comment.
- **6.5 Block.** IM windows have a **Block…** button that asks first, then hides the buddy's messages and invitations everywhere; the IM says "You've blocked Bob Brown." and the button becomes **Unblock**. Blocked buddies show struck through on the Buddy List.
  - Blocking uses Matrix's ignore list (`m.ignored_user_list`), so it applies in all your clients and the server leaves the person's events out. The SDK empties every conversation's cache when the list changes, so open windows now reload a page of history instead of going blank. The Buddy List rebuilds on ignore-list changes, and each DM now carries the other person's ID.
- **6.6 Preferences window.** **Preferences…** on the Buddy List (whose buttons are now two by two) opens a window with an auto-reply switch (off by default; 6.7 makes it work), a font and size for reading conversations, and the color your messages are sent in, with a sample line. OK applies the changes to every open conversation at once, and they persist across restarts. The font only changes how conversations look here; the color goes out with your messages (as `data-mx-color`), for any text you haven't colored yourself.
  - `src-tauri/src/preferences.rs` keeps them as JSON in the app's config folder, saved by writing a temporary file and renaming it. Damaged files fall back to the defaults, older files missing newer settings still load, and out-of-range values are reset. Windows get changes as `preferences:update` and apply fonts through CSS variables.
- **6.7 Auto-reply.** With auto-reply ticked in Preferences and you away, AIMtrix answers a buddy's IM with "Auto-reply: *your away message*": once per conversation per time away (coming back and going away again starts over), only in IMs, never to your own messages, edits, notices, or anything sent before you went away. The reply is an `m.notice`, encrypted in encrypted rooms, so two people away can't loop. It works while AIMtrix is running. The Away Message window says whether auto-reply is on, with a Preferences… button.
  - `matrix/auto_reply.rs`: a pure decision function (unit-tested rule by rule) and sync event handlers. Room keys come over a separate connection from messages, so a message can arrive before its key; such messages are retried for up to a minute before deciding. While away with auto-reply on, the log says why an IM got no reply (never its text). The presence tracker records when you went away, and `rooms::kind_of` decides IM vs. Chat Room with the Buddy List's rules.
  - Test fixes: the presence test watches from a throwaway user (every Buddy List test's presence updates were rate-limiting alice), `knows_device` asks the server for devices directly, and the Add Buddy test waits for the new DM's encryption state.
- **6.8 Packaging.** AIMtrix builds as a `.deb` (package `aimtrix`) and an `.AppImage` that install and run on clean Ubuntu 22.04, Debian 12 and Ubuntu 24.04: Sign On, signing on, and resuming the saved session after a restart all work. It has an original app icon (a yellow speech bubble with typing dots, from `src-tauri/icons/app-icon.svg`) in place of Tauri's. Sign On now has a Server dropdown (matrix.org by default, Custom… for anything else, plus the dev servers in dev builds) and remembers the last server. On Linux, windows no longer go black where another window covered them.
  - `mise run package` (`dev/build-package.sh`) builds in an Ubuntu 22.04 container, since packages built on a rolling distro need its glibc (and the AppImage bundled libraries needing glibc 2.44). `mise run test-package [image]` installs the `.deb` on a clean container, signs on as a throwaway user by typing into the window, and checks the restart resumes, leaving screenshots.
  - `mise run release` tags HEAD and pushes the tag; `.github/workflows/release.yml` builds on Ubuntu 22.04 and attaches both packages to a draft prerelease. Until going public, versions are `0.0.1-<seconds since midnight UTC>` (`dev/set-version.mjs`), carried by the tag and never committed. Other tasks are in `mise.toml`.
  - The product name is lowercase `aimtrix`, so Tauri's package name has no stray dash; a desktop-entry template keeps the menu name AIMtrix. The `.deb` depends on `ca-certificates` (a bare system without them couldn't connect) and recommends a keyring and an emoji font. Errors from building the client now include their cause. `main.rs` sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` on Linux unless already set.

## Phase 5: Encryption

### Changes
- **5.1 Encrypted rooms.** Messages in encrypted rooms send and read both ways with Element, in DMs and Chat Rooms. This worked with no app changes, since the SDK's end-to-end encryption was already on. Messages sent before this device signed on still can't be read (see 5.2 and 5.3).
  - New server test `encrypted_rooms_send_and_receive_both_ways`: two fresh AIMtrix devices exchange messages in the seeded "Carol Chen" DM and "Secret Chat", after checking that both rooms are encrypted.
- **5.2 Unable to decrypt.** Messages that can't be decrypted show as "*Name*: (encrypted message…)" with the likely reason: waiting for the key, sent before this computer signed on, sent before you joined, the sender didn't share the key, or from an unverified device. When the key arrives, the line turns into the real message in place. Reply previews of such messages say "an encrypted message".
  - `timeline.rs` has a new `Undecryptable` line with an `UndecryptableReason` taken from the SDK's `UtdCause`. Retrying is left to matrix-sdk, which decrypts again whenever new keys arrive.
  - `matrix-sdk-crypto` is now a direct dependency (same 0.19.1 already in the build), since `UtdCause` isn't re-exported by `matrix-sdk`.
  - New server test `undecryptable_messages_turn_into_text_when_keys_arrive`: a second Alice device sees the placeholder for Carol's message, then imports room keys exported from the first device and the placeholder becomes the text.
- **5.3 Recovery key.** A Restore Messages window asks for your recovery key or passphrase when the account has recovery set up but this computer doesn't have its keys yet. It opens by itself after sign-on (or when recovery is set up elsewhere mid-session), and the Buddy List shows "🔒 Older messages are locked. [Restore…]" until it's done. Once restored, keys for old messages download from the key backup and their placeholders turn into text. A wrong key says so; extra spaces are ignored; the key is never logged and is cleared from the window after use.
  - New `matrix/crypto.rs`: recovery state (`recovery:status` event, `recovery_status` command), `recover` with friendly errors, and `open_recovery`. Clients now download all backed-up room keys as soon as recovery unlocks them (`BackupDownloadStrategy::OneShot`).
  - The 5.2 placeholder now uses the existing `.aim-msg--undecryptable` style with a 🔒. `/demo` shows the Restore Messages window and the Buddy List row.
  - Dev builds optimize the hash crates (`sha2`, `hmac`, `pbkdf2`): recovery passphrases take ~2 s instead of ~10 s each.
  - New server test `recovery_key_lets_a_new_device_read_old_messages`, using bob with a fixed test passphrase (see `dev/README.md`). Found that resetting the identity while syncing loses the new cross-signing keys; logged for 5.5.
  - Fix: Close and Not Now did nothing, because the `recovery` window was missing from `capabilities/default.json` (no events, no closing). It's now listed, and windows may close themselves (`core:window:allow-close`).
- **5.4 Emoji verification.** A Verify This Computer window verifies this device against another of your sessions by comparing 7 emoji. Start it with **Verify…** on the Buddy List (shown with a 🔒 "This computer isn't verified." row, next to **Restore…** when recovery is also pending), or accept a request from Element's session list, which opens the window by itself. Compare the emoji, click **They Match**, and the session list in Element shows this computer as verified. Mismatches, timeouts and cancels say why; closing the window cancels on both sides. Afterwards the SDK fetches missing secrets from the other session.
  - New `matrix/verify.rs`: a `Flow` follows one verification (either side asking) and reports `Step`s (`verification:step` event); `Trust` says whether this device is cross-signed (`verification:trust` event). Commands `verify_device`, `accept_verification`, `start_verification`, `confirm_verification`, `cancel_verification`, `verification_step`, `device_trust`. Only requests from your own sessions are handled for now.
  - If both sides start the emoji comparison at once, it stalls. So only the side that asked starts it; when the other session asked, AIMtrix waits for it, with a **Start** button in case it waits for us.
  - New server test `emoji_verification_makes_a_new_device_trusted`. Encryption tests now wait until the sender knows the receiver's new device (`knows_device`), and server tests run with `--test-threads=8` (CLAUDE.md), since 16 threads overloaded the dev server.
- **5.5 New-account setup.** Accounts without a cross-signing identity get one at sign-on (no extra password prompt), so a new account's first device is verified straight away. When the account has no recovery, the Buddy List shows "🔒 Recovery isn't set up. [Set Up…]", opening a Set Up Recovery window: **Set Up** turns on key backup and shows the recovery key once, with **Copy** and an "I've saved my recovery key" checkbox before **Done**. The key works in Restore Messages on another device. If the account's identity came from another app and this computer lacks its keys, the window asks you to verify first instead of resetting anything.
  - `crypto.rs`: `setup_check` (`Setup`: ready, verify-first, already-set-up) and `set_up`, which returns the key straight to the window (never logged or sent as an event). `EncryptionSettings::auto_enable_cross_signing` is on. Commands `open_setup_recovery`, `setup_recovery_check`, `setup_recovery`.
  - New server test `new_accounts_get_a_recovery_key_that_restores_elsewhere`, on a throwaway user registered with the dev server's shared secret and deactivated afterwards (test-only `hmac`/`sha1` dependencies).
  - New `dev/clean-devices.py` removes leftover test devices, which had slowed encryption tests until they timed out (alice had 55). Tests now wait up to 30 s for a message.

## Phase 4: Chat Room window

### Changes
- **4.1 Chat Room window.** Group rooms now open in a Chat Room window (`/chat`, titled "*Name* - Chat Room", 540×400 to leave space for the member list). DMs still open as IMs. `windows::open_room` chooses the window from the room's DM/group kind.
  - The message list and the compose box (toolbar, editor, typing notices, Send) are now shared components in `src/lib/conversation/` (`Transcript.svelte`, `Compose.svelte`), used by both windows. The status bar text is in `status.ts`.
  - The IM window is now built from these components and should look the same as before.
  - The Chat Room in `/demo` now shows the formatting toolbar.
- **4.2 Member list.** The Chat Room has a member pane on the right with the count ("3 people here") and each member's Buddy Icon and display name, sorted by name. It updates live when someone joins or leaves, or changes their name or avatar.
  - `matrix/members.rs` loads the joined members and resends the whole list as a `room:<key>:members` event on every member event and whenever an icon finishes downloading. Windows fetch the first list with the `room_members` command.
  - The watch stops when the window closes or you sign off.
- **4.3 Room events.** The conversation shows system lines for room events: "*Name* has entered the room.", "has left the room.", "was invited.", "was removed from the room." and "was banned from the room.", plus "*Name* changed the topic to: …" and "removed the topic." The Chat Room shows the current topic in a bar at the top, updated live. The lines show in IM windows too, since both share the transcript.
  - `timeline.rs` has new `Membership` and `Topic` lines. Accepted invites count as entering; declined invites and knocks get no line.
  - The Chat Room watcher (`members.rs`) now follows the topic as well. The `room_members` command became `chat_room`, which returns members and topic; topic changes arrive as `room:<key>:topic` events. The frontend helper is `watchChatRoom` in `src/lib/chatroom.ts` (was `members.ts`).

## Phase 3: IM window

### Changes
- **3.1 Open window.** Double-clicking a buddy opens an IM window labelled `room-<key>`, where the key is an FNV-1a hash of the room ID (labels and event names can't contain `!`). Opening it again focuses the window and restores it if minimized. Invitations don't open.
- **3.2 Read messages.** `timeline::watch` subscribes to the room's timeline and sends `room:<key>:timeline_diff` events. Each timeline item becomes exactly one display line, so the window applies diffs by position. Messages show as "Name: text" in AIM colors, with display names loaded from the member list.
- **3.3 Send.** Added the message box: Enter sends, Shift+Enter or Alt+Enter adds a new line. Sent messages show up straight away (local echo); one the server rejects is marked "(not sent)" and its text comes back for another try. Emotes (`/me`) show as "* Name text".
  - Bug fixes: signing off could hang because of a stop race in the SDK's `SyncService` (`Syncing::stop` now re-sends the stop request every 100 ms), and the dev Synapse's room-creation rate limit (`rc_room_creation`) was relaxed. The "Known issues and follow-ups" section was added to `PLAN.md`.
- **3.4 Scrollback.** Older messages load as you scroll up (or until the window can scroll), keeping your reading position, until "This is the beginning of the conversation."
- **3.5 Typing.** Sends typing notices (renewed every 2 s, stopped after sending or 5 s idle) and shows "Name is typing…" in the status bar.
- **3.6 Formatting.** Bold, italic, underline and an 8-color text palette, typed in a contenteditable editor and sent as `formatted_body`. Pasted text arrives unformatted.
  - Incoming and outgoing HTML is cleaned in Rust (`matrix/html.rs`, ammonia): only Matrix's formatting tags are kept, colors must be `#rrggbb`, links must be http(s), mailto or matrix, and `<script>`/`<style>` are removed.
  - Matrix's `data-mx-color` is applied in the window, and links don't navigate it.
- **3.7 Buddy icon pane and read receipts.** The IM window shows the buddy's icon and yours at 96 px. A read receipt is sent while the window has focus (300 ms debounce), which clears the bold in the Buddy List.
- **3.8 Other message types.** Images show as thumbnails (downloaded and decrypted in encrypted rooms; full images over 10 MB are skipped). Files show with an icon and size. Edits show "(edited)", deletions show "(message deleted)", and replies show "In reply to *Name*: preview", loading the original message if needed.
- **3.9 Save attachments.** Clicking a file or image opens a native Save dialog (`tauri-plugin-dialog`, run from Rust) and saves the file there, decrypted when needed. The status bar shows "Saving…" and then "Saved *name*". Unsafe file names are cleaned up before saving.
  - Fixed flaky timeline tests: rooms with an open window now get a sliding-sync subscription (up to 20 events per sync instead of 1), so a burst of messages no longer resets an open conversation. Tests now find seeded rooms by their `aimtrix.seed` marker, not by name.

## Phase 2: Buddy List

### Changes
- **2.1 Room classification.** Pure functions in `matrix/rooms.rs` sort rooms into DM or group, and into Favorites, Buddies, Chats or Invitations, with unit tests. A room counts as a DM if it is in `m.direct` or has at most 2 joined+invited members; the `aimtrix.chat` tag forces a group. The tests cover stale `m.direct` lists.
- **2.2 Room list events.** Watches the SDK's room list and sends `buddylist:update` to windows whenever it changes.
- **2.3 Buddy List window.** Collapsible groups with "(n)" counts and display names.
- **2.4 Unread and ordering.** Rooms with unread messages are bold, and the list is sorted by most recent activity.
- **2.5 Buddy Icons.** Avatar thumbnails are downloaded with authenticated media and cached (on disk in the SDK store, and as `data:` URLs in memory). Rooms without an avatar get an original default icon for DMs or chats.
- **2.6 Invitations.** Invites have their own group with Accept and Decline. An accepted room moves into the right group.

## Phase 1: Sign On

### Changes
- **1.1 First login.** Added matrix-sdk and a `login` command (homeserver, username, password) that returns the user ID. Access tokens are never logged.
- **1.2 Sign On window.** The Sign On form, which shows errors and closes once you're signed on.
- **1.3 Session restore.** The session is saved in the OS keyring (`matrix/keyring.rs`), with an SQLite store per session. On launch the app resumes into the Buddy List or opens Sign On. Added `logout`. Windows are now created in code (`windows.rs`).
- **1.4 Sync.** Sync starts after sign-on, and the Buddy List shows the connection status (connecting, online, offline, error) and recovers on its own. If the server rejects the saved token, the session is forgotten and Sign On opens with an explanation.

## Phase 0: Foundations

### Changes
- **0.1 Test homeserver.** `dev/docker-compose.yml` runs Synapse (presence on) and Element Web. `dev/seed.py` creates alice, bob and carol, plain and encrypted DMs and groups ("Test Chat" with about 60 messages for scrollback, "Secret Chat"), and an invitation. Seeded rooms are marked with an `aimtrix.seed` state event, so re-running the script is safe.
- **0.2 Scaffold.** Tauri v2 app with a SvelteKit frontend (Svelte 5, TypeScript, static SPA).
- **0.3 AIM chrome CSS.** `src/styles/aim-chrome.css` styles the window frame, title bar, buttons, lists, text boxes and status bar in a Win98/XP look. `/demo` shows each piece. All art is original.
